理论接口 · 这个页面在演示什么Theory interface · what this page shows

一份一千七百万行的证明，没有人读得完；但谁都可以让机器替自己从头查一遍。本页把“怎么查”画成两个场景：CI 怎样把 Main 切成可以分头编译、凭内容复用的分片；读者怎样在自己的机器上，不信任 CI、不信任作者，把这些分片重放一遍。本页是示意模型加真实数字，不是证明。

  1. 分片 DAG（示意）。横轴是依赖层 0 … 35，Main 在最右边独占一层。CI 把 Main 的真实导入闭包切成 8,490 个分片，每片至多 400 个模块、2,500,000 字节；分片的层号就是它最长的导入链。舞台上的 299 个点是按比例缩小的示意图，边由固定种子生成。
  2. CI 波。时间轴走到第 k 层，第 k 层以下全部编译完（绿色：Lean 在编译时已逐条检查过内核），第 k 层正在编译（琥珀色），其余还在等（青色）。上游 README 写明：首批 17 个编译键之后，立刻有 529 个任务可以并行；剩余路径更长的任务先派发。下方小图是 36 层的波前：两端是真数，中间的形状是示意。
  3. 内容寻址与复用。一个分片的键覆盖它的源码、它所导入分片的键、构建配置、工具链与钉住的依赖包。改动一个模块，它所在分片的键就变了；所有直接或间接导入它的分片，键里都含着它的键，于是也跟着变，一直到 Main（品红的失效锥）。锥外的分片键不变，Release 里现成的产物原样复用（绿色）。页面真的用 SHA-256 算了每个示意分片的键，改动之后变了键的恰好是失效锥。
  4. 零信任重放（示意路线）。读者只需四行：git clone、./verify --status Main、可先试小模块 ./verify BuildAid.D1、再 ./verify Main。脚本从 16 个 Release 拉回分片，逐片核对 Release 公布的 SHA-256；再用 lake env leanchecker --fresh 在空白的 Lean 环境里把模块及其导入的每条声明重放一遍；最后核对五条顶层定理的公理只落在 propext、Classical.choice、Quot.sound 之内（ci/Audit.lean 用 #print axioms 做同样的事）。
  5. 陈述与多校验器。src/Challenge.lean 只依赖 Mathlib v4.33.1（提交 0df444a360ea），写下五条陈述；Comparator 核对 Main 证明的类型与它逐条相同，公理不出那三条，再交给 Lean 4.36 内核与 leanchecker-paranoid、nanoda、con-leche、con-ron 在断网的 bubblewrap 沙盒里各查一遍；lean4lean 用 Lean v4.33.1 另行构建、单独运行。这条多校验器路线在整个提交上的完整运行是数小时的长任务，本页只画它的规则。
  6. 试着作弊。伪造 .olean：下载的字节和 Release 公布的校验和对不上，SHA-256 当场拦下；如果伪造者连 Release 的校验和也一起改了（CI 本身在撒谎），校验和对得上，但空白内核会把调包的证明重新检查一遍并拒绝它，所以下载 CI 的分片不需要信任 CI。偷塞 sorry 或自定义公理：内核接受公理声明，公理审计在闭包里看到 sorryAx 而拒绝。改写陈述：证明本身是对的，内核与公理审计都放行，只有 Challenge 的陈述比对能发现它证的不是那道题。

书中：第七章 · 三十五行挑战契约 · 8,490 块分片与诚实边界声明

Nobody can read a proof of seventeen million lines, but anyone can have a machine check it from scratch for them. The page draws how in two scenes: how CI cuts Main into shards that compile separately and are reused by their content, and how a reader replays those shards on their own machine, trusting neither CI nor the author. The page is an illustrative model with real figures, not a proof.

  1. Shard DAG (illustrative). The horizontal axis is the dependency level 0 … 35, with Main alone in the last level on the right. CI cuts the real import closure of Main into 8,490 shards of at most 400 modules and 2,500,000 bytes; a shard's level is its longest chain of imports. The 299 dots on the stage are a scaled-down illustration whose edges come from a fixed seed.
  2. The CI wave. When the rail reaches level k, every level below k is compiled (green: Lean checked each declaration in its kernel while compiling), level k is compiling (amber) and the rest wait (cyan). The upstream README says that 529 jobs are eligible at once after the first 17 compilation keys, and that jobs with longer remaining paths go first. The small plot below is the 36-level wavefront: its ends are real, the shape in between is illustrative.
  3. Content addressing and reuse. A shard's key covers its sources, the keys of the shards it imports, the build configuration, the toolchain and the pinned packages. Edit one module and the key of its shard changes; every shard that imports it, directly or not, carries that key inside its own, so its key changes too, all the way up to Main (the magenta invalidation cone). Outside the cone the keys stay the same and the outputs already in the Releases are reused (green). The page really computes the SHA-256 key of every illustrative shard, and the keys that change after an edit are exactly the cone.
  4. Zero-trust replay (illustrative route). A reader needs four lines: git clone, ./verify --status Main, optionally the small module ./verify BuildAid.D1, then ./verify Main. The script pulls the shards from 16 Releases and checks each against the SHA-256 the Release publishes; lake env leanchecker --fresh then replays every declaration of the module and its imports in an empty Lean environment; last, it checks that the five headline theorems use no axioms beyond propext, Classical.choice and Quot.sound (ci/Audit.lean does the same with #print axioms).
  5. Statements and several checkers. src/Challenge.lean depends on Mathlib v4.33.1 (commit 0df444a360ea) alone and writes down the five statements; Comparator checks that the types proved in Main are those statements, that no axiom beyond the three is used, and hands the proof to the Lean 4.36 kernel and to leanchecker-paranoid, nanoda, con-leche and con-ron in a bubblewrap sandbox without network; lean4lean is built with Lean v4.33.1 and run separately. A full run of this route on the whole submission takes many hours; the page draws its rules only.
  6. Try to cheat. A forged .olean: the downloaded bytes do not match the checksum the Release publishes, and SHA-256 stops it at once; if the forger also rewrote the Release checksum (CI itself lying), the checksum matches, but the empty kernel checks the swapped proof again and refuses it, which is why downloading CI's shards needs no trust in CI. A smuggled sorry or a custom axiom: the kernel accepts an axiom declaration, and the axiom audit sees sorryAx in the closure and refuses. A tweaked statement: the proof itself is fine, the kernel and the axiom audit let it through, and only the comparison with the Challenge statements finds that it proves a different theorem.
